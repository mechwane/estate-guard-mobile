# Estate Guard — Backend Handover Package

This document explains how to recreate the Estate Guard backend inside a
fresh Supabase project owned by you or your client.

> **Important:** The current backend runs on **Lovable Cloud**, which is a
> managed Supabase instance provisioned by Lovable. It **cannot be
> directly transferred** to another Supabase account — the project ref,
> service role key, and DB password are not exposed to end users on
> Lovable Cloud. What we CAN do (and this package documents) is
> **recreate** the same schema, functions, RLS policies, and storage
> buckets inside any Supabase project by running the shipped migrations.

The app itself is fully portable. Only the `.env` values and generated
types have to be swapped.

## 2. Prerequisites

- A Supabase account: <https://supabase.com>
- The Supabase CLI: <https://supabase.com/docs/guides/cli/getting-started>
  - Verify: `supabase --version`
- Node 20+ and `bun` (or `npm`) installed locally.
- Access to this repository.

---

## 3. Create a new Supabase project

1. Log in at <https://supabase.com/dashboard>.
2. **New project** → pick org, name (e.g. `estate-guard`), strong DB password, closest region. Save the password.
3. From **Project Settings → API** copy:
   - `Project URL`
   - `Project ID` (the ref, e.g. `abcdxyz`)
   - `anon` publishable key (`sb_publishable_…` or legacy `eyJ…`)
   - `service_role` secret key (`sb_secret_…` or legacy `eyJ…`) — **server-only, never ship to browser**.

---

## 4. Link the CLI and run migrations

From the project root:

```bash
supabase login
supabase link --project-ref <YOUR_NEW_PROJECT_REF>
supabase db push
```

`supabase db push` applies every file in `supabase/migrations/` in
timestamp order. That single command recreates:

- All enums (`app_role`, `estate_status`, `verification_status`,
  `occupant_type`, `resident_pass_kind`, etc.)
- All 43 public tables (see the inventory in section 9)
- All RLS policies and GRANTs
- All triggers and updated_at helpers
- All SECURITY DEFINER RPCs (see section 10)
- The `handle_new_user` trigger on `auth.users`

If a migration fails, fix the reported issue and re-run
`supabase db push`. Migrations are idempotent as a set — do not edit
already-applied migration files after they've run in production.

### Verifying

```bash
supabase db lint
```

In the Supabase dashboard, open **Database → Tables** and confirm the
table count matches section 9.

---

## 5. Create storage buckets + policies

Run `supabase/storage.sql` in **SQL Editor** (or `psql`) against the new
project. It creates the two required private buckets and the RLS
policies used by the app:

- `avatars` — private. Users read/write only their own folder (`<uid>/…`).
- `verification-docs` — private. Residents upload only into their own folder; estate admins and super admins read within their estate.

Signed URLs are generated by the app on demand.

---

## 6. Configure Auth

In **Authentication → Providers**:

1. **Email**: enable. Leave "Confirm email" ON unless the client wants magic-link only.
2. **Google** (optional but recommended): enable and add a Google OAuth client. Add the callback URL from the Supabase provider config to the Google Cloud console. In the app, sign-in already routes through the standard Supabase client, so no code change is needed.

In **Authentication → URL Configuration**:

- **Site URL**: the client's production URL.
- **Additional redirect URLs**: any preview URLs (e.g. `http://localhost:8080`, staging domains).

In **Authentication → Rate Limits**: leave defaults; raise `Auth emails per hour` only if you're sending your own signup traffic.

---

## 7. Update the app's environment variables

Edit `.env` in the project root:

```
VITE_SUPABASE_URL="https://<PROJECT_REF>.supabase.co"
VITE_SUPABASE_PUBLISHABLE_KEY="<anon publishable key>"
VITE_SUPABASE_PROJECT_ID="<PROJECT_REF>"

SUPABASE_URL="https://<PROJECT_REF>.supabase.co"
SUPABASE_PUBLISHABLE_KEY="<anon publishable key>"
SUPABASE_PROJECT_ID="<PROJECT_REF>"
```

If the app uses any server function that calls `supabaseAdmin` (see
`src/integrations/supabase/client.server.ts`), also set on your host:

```
SUPABASE_SERVICE_ROLE_KEY="<service_role secret key>"
```

**Never commit the service role key.** Add it as a secret on your
hosting provider (Vercel/Cloudflare/Netlify env, or Supabase Edge
Function secrets if you deploy edge functions later).

See `ENVIRONMENT.md` for full details.

---

## 8. Regenerate TypeScript types

```bash
supabase gen types typescript --project-id <YOUR_NEW_PROJECT_REF> --schema public \
  > src/integrations/supabase/types.ts
```

Then:

```bash
bun install
bun run build
```

The build should succeed with zero TypeScript errors. If a type name
diverges from the Lovable Cloud copy (unlikely — the schema is the
same), fix by re-running the types generator.

## 10. Creating the first Super Admin

The Super Admin role is **never granted through the app UI** (that would
be a privilege-escalation surface). Grant it directly against the DB:

1. In Supabase dashboard → **Authentication → Users**, invite the
   Super Admin's email. They set their password via the invite link.
2. Copy their `id` (UUID) from the user list.
3. Open **SQL Editor** and run:

```sql
-- Replace with the real UUID
INSERT INTO public.user_roles (user_id, role)
VALUES ('<USER_UUID>', 'super_admin')
ON CONFLICT DO NOTHING;

-- Ensure their profile is approved and not tied to a single estate.
UPDATE public.profiles
SET approved = true, estate_id = NULL
WHERE id = '<USER_UUID>';
```

That's it. They can now sign in and land on `/app/super`.

## 11. Inviting Estate Admins

Super Admin flow (in-app):

1. Create the estate: `/app/super` → **New estate**.
2. Open the estate detail page → **Invite estate admin** → paste the
   admin's email. This calls `create_estate_admin_invite` and returns a
   one-time token.
3. Share the token with the invitee. After they sign up with the same
   email, they call `redeem_estate_admin_invite(token)` from the app
   (already wired into `/app/super/invites` and the invite acceptance
   flow). Their role becomes `estate_admin` for that estate.

## 12. End-to-end smoke test

After migrations + env swap:

**Super Admin**
- Sign in → `/app/super` dashboard loads with real counts.
- Create an estate → status = pending → activate it.
- Invite an estate admin → copy token.
- Register an access device on `/app/super/devices` → status changes work.
- Toggle a feature flag on `/app/super/features`.

**Estate Admin**
- Redeem invite → land on `/app/admin`.
- Approve a pending resident on `/app/admin/verifications`.
- Assign a guard on `/app/admin/staff`.
- Manage a resident's biometric access on `/app/admin/residents`.

**Resident**
- Sign up with the estate code → submit verification with a document
  upload (checks `verification-docs` bucket policies).
- Issue a resident pass (checks WebAuthn challenge).
- View biometric access status on their profile.

**Guard**
- Validate a guest code → check-in → check-out on `/app/guard`.

**RLS spot checks (SQL editor as an authenticated user)**
- Resident cannot `select * from public.bills where resident_id <> auth.uid()`.
- Estate admin cannot see other estates' `guest_invites`.
- Anon cannot select from `profiles`.

**Auth**
- Password reset flow completes end to end.
- OAuth (if enabled) returns to the correct redirect.

**Storage**
- Signed avatar upload works.
- Verification doc upload works, download requires signed URL.

## 13. Known limits of an automated migration

- **User data does not move**: `auth.users`, sessions, and per-user
  storage objects live only in the Lovable Cloud project. A migration
  gives you the schema, not the data. If you need to move real data,
  export it separately (SQL COPY for public tables; Supabase Auth
  export for users) and load it into the new project.
- **Service role key**: Lovable Cloud does not expose it. The new
  project's service role key is generated when you create the project.
- **Edge Functions**: None are used by this app (all server-side logic
  is TanStack Start server functions + SECURITY DEFINER RPCs). Nothing
  to port there.
- **Custom domain / email sender**: Reconfigure in the new project's
  dashboard.

---

## 14. What's intentionally NOT in this package

- No demo passwords, no seeded admin accounts, no fake residents.
- No sample payment / billing data.
- No VTU airtime/data — that surface has been removed from the UI. The
  legacy `vtu_providers` / `vtu_transactions` tables remain only so
  historical data (if any) is preserved; no new writes happen from the
  app.
- No service role key values anywhere in the repo.
